The three things that cost the most

Read off the same measurements, not a separate model.

  1. The CEF runtime, counted once per process (587 MiB of the 940 MiB)

    RSS sums every process in the tree, and each of the 10 processes maps the same 277 MB libcef.so from the package. The gap between summed RSS (940 MiB) and summed Pss (353 MiB) is that double count. It is not memory the app can give back, but a budget written as "total RSS" pays for it once per process, so the number of processes is itself a cost.

  2. One browser context per space (130 MiB per extra parked space)

    4 spaces cost 1335 MiB against 940 MiB for 1: 130 MiB per space. Parking a space (WasHidden(true)) throttles its timers but does not drop its browser: with all four awake the tree measures 1312 MiB against 1335 MiB parked — within 2 % of each other, so parking buys no memory at all. Parking is a CPU knob, not a memory one.

  3. Snapshot cost scales with the page, not with the viewport (26 µs per element)

    p50 goes from 5 ms at 21 elements to 66 ms at 2412 elements and 141 ms at 3797 elements. Filtering to the viewport does not avoid that work: the same call without the filter (`scope: "full_page"`) costs 71 ms instead of 66 ms on the long list and 154 ms instead of 141 ms on the dashboard, because Accessibility.getFullAXTree reads the whole document before anything is filtered out. The host socket is not the cost: the same call against the bridge's own headless Chrome, with no app process in between, takes 74 ms against 66 ms here.
