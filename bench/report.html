Spaces in one profile share a browser context, so each extra space is one more renderer and little else. A second profile is a separate browser context with its own renderer and cache, and it measures about the same at idle — isolation is close to free here; what costs 355 MiB is the first browser.

What the 0.4.0 fixes changed

The §6 targets were guesses written before anything was measured. They have not been moved; these rows are where the build changed.

  • Cold start to first paint — 0.4.0 fixes the at-spi stall that could keep the first page blank for ~16 s
  • Memory, one tab open (PSS) — 0.4.0 reports memory as PSS instead of summing RSS over 10 processes
  • Extra memory for a 2nd space — profiles are the isolation boundary now, so spaces in one profile are tab sets, not separate browser contexts
  • Extra memory for the 4th space — the same model change
  • Snapshot p50, viewport — 0.4.0's serializer: scope header, no duplicated url=, no label-echo children, no empty generic wrappers
  • Snapshot p95, viewport — the same serializer change
  • Snapshot p50, full page — the same serializer change (full page shrank from ~551k to ~330k chars on a Wikipedia page)
  • Snapshot p95, full page — the same serializer change

The three things that cost the most

Read off the same measurements, not a separate model.

  1. The Chromium payload itself (355 MiB of PSS, 575 MiB of it counted twice as RSS)

    One idle tab is 355 MiB of PSS across 10 processes; adding up each process's RSS gives 930 MiB for the same bytes. A stock headless Chrome on the same box is 315 MiB of PSS for one page, so what is left is Chromium, not anything this app's shell adds on top: the app's own browser process (GTK plus CEF's browser side) accounts for 154 MiB of it, and the rest is renderer, network service and zygote.

  2. Spaces and profiles are no longer the cost (16 / 27 / 22 MiB each)

    A second space adds 16 MiB of PSS, a third or fourth adds 27 MiB, and crossing into a second profile adds 22 MiB. The old per-space figure of 130 MiB was summed RSS over 4-vs-1 spaces when each space also had its own browser context — a real measurement of the wrong quantity. With the profile as the isolation boundary, concurrency is cheap; the fixed cost is the single browser underneath it.

  3. Acting on a page costs far more than reading it (407 of 523 ms in one round)

    One round is 523 ms: opening the page 118 ms, clicking a button 127 ms, typing 15 characters 162 ms, while the snapshot of that page is only 23 ms and the command-line tool starting up 51 ms. Each action is its own round trip plus the SDK's action boundary, so the interaction path — not the snapshot serializer — is where an agent's wall time goes on ordinary pages. Reading a heavy one is still expensive when an agent gets there: the 3797-element dashboard takes 187 ms p50 and — ms p95 to snapshot, against a 40 ms budget.

Methods in bench/README.md, raw numbers in bench/results.json. Every figure is the median of 3 runs (spread = max − min); memory is the sum of /proc/<pid>/smaps_rollup over the app's whole process tree, reported as PSS (shared pages split between the processes mapping them) and as summed RSS (shared pages counted once per process). The box is shared: other builds and QA runs can be active during a pass, so treat small differences as noise.
